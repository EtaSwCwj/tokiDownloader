# 2026-09-08 작품 전체 ZIP과 회차 목록 페이지 누락 수정

## 사용자 요구와 확인된 원인

- 압축 단위는 회차별 ZIP이 아니라 **작품 전체 ZIP 하나**다. 여러 작품을 선택하면 작품당 하나씩 만든다.
- 사용자가 제시한 `/manhwa/34732?page=2` 화면에는 첫 페이지에서 빠진 이전 회차가 있었다.
- 실제 접속 확인 시 회차 페이지는 `nav.theme-episode-pager`와 `epage=2` 링크를 사용했다.
  기존 다운로더는 `ul.pagination li[class="active"]`만 검사해 첫 페이지 100개에서 끝났다.
- 이전 연결 장애 수정 당시의 '사이트 목록 100개 완료'는 첫 페이지만 검사한 결과였다.
  사이트 전체 완료를 입증하지 못한 판단이었으며, 이번 전체 페이지 확인으로 정정한다.

## 구현

### 전체 회차 목록

- `downloader_pagination.js`: 신형 회차 전용 페이지와 구형 pagination 링크를 탐색한다.
- 같은 작품·같은 출처의 페이지 링크만 방문하고 댓글 페이지, 다른 작품, 중복 주소를 제외한다.
- 페이지별 회차를 합친 뒤 안정적인 회차 ID로 중복 제거하고 정렬한다.
- 총 회차 수 미달, 다른 페이지의 동일 목록 반복, 리다이렉트 반복, 빈 목록, 탐색 한도 초과는
  일부 수집 결과로 완료 처리하지 않고 실패로 보고한다.
- `listPageCount`, `siteEpisodeCount`를 메타데이터에 남기고 페이지별 수집 수를 로그로 출력한다.

### 작품 ZIP

- 서비스·CLI·수동 GUI·자동 압축 모두 기본 단위 `work`.
- 결과: `<작품>/_archives/<작품 폴더 전체 이름>.zip`.
- 내부: `000001 회차 전체 제목/000001.jpg`와 같은 고정 자릿수 회차/페이지 순서.
  원본 폴더 이름은 변경하지 않으며, 예전 축약명 대신 메타데이터의 전체 표시 제목을 사용한다.
- `metadata.json`, 표지는 ZIP 안에도 포함하고 외부 작품 폴더에도 보존한다.
- 원본 정리는 ZIP 전체 CRC 검증과 카탈로그 저장 후, 압축 당시 크기/수정시각이 같은 회차 파일에만 적용한다.
- 기존 ZIP만 남은 회차를 스트리밍으로 새 ZIP에 합치므로 새 회차 추가 시 기존 회차를 잃지 않는다.
  재검토로 목록 순번이 바뀌면 안정적인 ID를 기준으로 내부 순서도 갱신한다.
- ZIP 작성 취소·실패·카탈로그 저장 실패 시 이전 ZIP을 보존/복구한다.
  외부에서 변경한 ZIP이나 앱 소유 기록이 없는 ZIP은 덮어쓰지 않는다.
- 기존 회차별 ZIP을 합칠 수 있지만 기존 ZIP 파일은 자동 삭제하지 않는다.
- Python/Node 카탈로그가 작품 ZIP의 여러 회차를 인식한다. Node는 ZIP64도 읽는다.
- 전체 이미지 버퍼를 메모리에 올리지 않고 1 MiB 청크로 처리한다. 회차 2,000개에서도
  기존 작품 ZIP 디렉터리는 회차별로 다시 열지 않는다(계획 수집에서 최대 2회).

## 남은 제한

- 완료 기록을 확인할 수 없는 원본 회차는 보존하고 압축 대상에서 제외한다.
- 작품 ZIP 갱신에는 기존 ZIP과 새 임시 ZIP을 함께 둘 디스크 공간이 필요하다.
- 프로세스 강제 종료/전원 중단의 두 파일(ZIP·카탈로그) 교체 경계는 완전한 트랜잭션이 아니다.
  교체 전 원본 ZIP의 `.toki-*.previous` 복구본이 남을 수 있다. 일반 예외는 자동 롤백한다.
- 외부 압축 뷰어 종류마다 재생 방식은 다를 수 있다. 실제 검증은 ZIP 내부 파일 순서와
  무결성까지이며 사용자 뷰어에서의 장시간 감상까지 자동 검증한 것은 아니다.
