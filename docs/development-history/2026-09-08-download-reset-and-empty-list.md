# 2026-09-08 다운로드 연결 실패 진단과 빈 목록 표시 수정

기준 커밋: `bf1ff72`. 사용자 캡처: `2026-09-08-09-18-39.png`.

## 확인된 사실

- 실제 작업 `747a0bd6d2`, 작품 `/manhwa/34732`의 26-2화(목록 순번 28)는
  8장 중 6장을 처리하고 2장 실패로 종료했다. 최종 상태는 `오류`, 분류는 `network`다.
- 09:17~09:18 로그에 이미지 CDN `aws-cdn9.site`의 `read ECONNRESET`이 반복된다.
  대표 이미지도 실패했다. 기본 이미지별 3회와 작품 자동 재시도 2회가 이미 실행됐다.
- 이미지 URL을 별도 Node HTTPS/Fetch, curl, 숨김 Chromium에서 확인해도 연결 reset이
  재현됐다. 일부 요청은 HTTP 200으로 283,353바이트를 받았지만 연속 성공은 아니었다.
  TLS 1.2 제한도 한 번 성공 후 다시 실패했으므로 TLS 버전 변경을 해결책으로 적용하지 않았다.
- 별도 저장 위치에서 실제 CLI를 동시 이미지 1개로 제한해 26-2화만 다시 받아도 이미지
  8개가 모두 실패하고 종료 코드 1이었다. 검증용 프로세스는 자체 종료됐으며 사용자 GUI
  다운로드를 재시작하거나 기존 원본을 삭제하지 않았다.

```powershell
node down.js -url "https://newtoki1.org/manhwa/34732" -start 28 -last 28 -output "logs\2026-09-08-download-reset-check" -image-concurrency 1 -provider-backoff 5 -json-events
```

CDN 또는 로컬~CDN 사이 연결 경로 문제로 범위를 좁혔지만 어느 구간이 reset하는지는
확정하지 못했다. 다운로드 성공으로 보고하지 않는다. SSL 인증서 검사 해제, CDN 주소
임의 치환, 프록시/시스템 네트워크 설정 변경은 하지 않았다.

## 수정

- `enqueue_download`에서 목록 카운터보다 먼저 `_add_job_card`가 상태 패널을 갱신해,
  실제 행이 추가돼도 `empty` 패널이 남았다. 카운터 증가 후 행/패널을 갱신하도록 순서를
  변경했다. 전체 기록 삭제 후 재등록도 같은 경로로 처리된다.
- 실제 CLI 통합 검사 중 짧은 ping(350 ms)이 지연되면 GUI가 꺼진 것으로 판단해
  직접 실행으로 내려가는 경우가 관측됐다. 연결 후 응답 제한 시간 초과는 실행 중으로
  취급해 별도 GUI 실행/오프라인 DB·파일 변경으로 우회하지 않도록 했다.
- 격리 CLI fixture는 실패 시 사용자 경로로 생산용 GUI를 시작할 수 없도록 막았다.

## 검증

- Python 전체 394건 통과. 실제 CLI 프로세스 → private IPC → 실제 MainWindow에서
  목록 4개 삭제 → 빈 화면 → 새 모의 다운로드 추가 → 새로고침 없이 `content`, 행 1개
  표시 → 다운로드 종료 후에도 표시 유지까지 검증했다. 네트워크 요청 없는 격리 데이터다.
- ping 응답 지연은 GUI 실행 중으로 판정하고 추가 프로세스를 시작하지 않는 단위 검사 포함.
- 사용자 GUI는 다운로드/파일 작업이 없는 상태에서 정상 종료 후 수정 버전으로 다시 열어
  실패 작업이 목록에 보이게 했다. 캡처: `logs/2026-09-08-download-error-visible.png`.
- 사용자 작업 기록과 받은 이미지는 유지했다. 검증용 다운로드 자료는 위 logs 폴더에 별도
  보존했다. 다운로드 연결 장애 해결은 미완료이며 UI 수정 검증과 구분한다.
